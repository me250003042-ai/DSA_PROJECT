# D3: Two-Heap Method for Running Median and Fixed Percentiles

## 1. Objective

The objective is to maintain the median and general fixed percentiles of a changing set of readings using two heaps.

The data can change through:
- Insertion of new readings.
- Expiration of old readings due to the sliding window.
- Retraction of existing readings.

The method should support efficient updates and percentile queries.

## 2. Basic Idea

We divide the active readings into two parts using:

- **Max-Heap L:** Stores the smaller readings. Its root contains the largest element in L.
- **Min-Heap R:** Stores the larger readings. Its root contains the smallest element in R.

Let:
- n = number of active readings.
- p = required percentile, where 0 < p ≤ 1.
- k = ceil(p × n).

We maintain:

    size(L) = ceil(p × n)

    size(R) = n - size(L)

The heap roots allow us to access the boundary between the two parts efficiently.

## 3. Invariants

The algorithm maintains three properties.

**Invariant 1: Size Property**

    size(L) = ceil(p × n)

**Invariant 2: Ordering Property**

Every active element in L is less than or equal to every active element in R.

    maximum(L) ≤ minimum(R)

**Invariant 3: Membership Property**

L contains the k smallest active readings, and R contains the remaining readings.

These properties ensure that the required percentile is available at the root of L.

## 4. Finding a Percentile

Since L contains the k smallest active readings, its maximum element is the k-th smallest element in the complete data set.

Therefore:

    p-th percentile = maximum(L)

Because L is a Max-Heap, the maximum element is available at its root.

After the heaps have been balanced for the requested percentile, retrieving the percentile takes O(1) time.

The implementation calculates the required rank using:

    k = ceil(p × n)

## 5. Finding the Median

The median is a special case of percentile calculation.

For an odd number of active readings:

    Median = maximum(L)

For an even number of active readings:

    Median = (maximum(L) + minimum(R)) / 2

The implementation uses the roots of the two heaps to calculate the median without sorting all readings.

## 6. Insertion Operation

When a new reading x arrives:

1. Clean invalid elements from the heap roots.
2. If L is empty or x is less than or equal to the root of L, insert x into L.
3. Otherwise, insert x into R.
4. Update the live element count.
5. Calculate the required size of L.
6. Rebalance the heaps.

During rebalancing:

- If L contains too many live elements, move its root to R.
- If L contains too few live elements, move the root of R to L.

Each heap insertion or removal takes O(log n) time.

For a fixed percentile, the required partition changes by at most one element after a single insertion. Therefore, insertion takes O(log n) time, assuming the heap storage is controlled by the purge policy.

## 7. Retraction Operation

A reading may be retracted even if it is not the most recently inserted reading.

To support arbitrary retractions, the implementation uses a custom hash table to track each reading's ID, active status and heap membership.

When a reading is retracted:

1. Find its ID in the hash table.
2. Check whether the reading is still active.
3. Mark it as deleted by removing its active hash-table entry.
4. Decrease the live count of the heap containing that reading.
5. Recalculate the required heap size.
6. Rebalance the heaps.

The implementation uses lazy deletion. A deleted reading does not need to be searched for and removed immediately from the middle of a heap.

Instead, invalid readings are removed when they reach a heap root.

This avoids expensive arbitrary removal operations from binary heaps.

## 8. Sliding-Window Expiration

The application maintains a window of the most recent w readings.

When the window is full and a new reading arrives:

1. Remove the oldest reading ID from the expiry queue.
2. Mark that reading as deleted.
3. Update the live count.
4. Rebalance the heaps.
5. Insert the new reading.

Thus, expired readings are handled using the same deletion mechanism as manually retracted readings.

## 9. Purging Lazy-Deleted Elements

Lazy deletion can cause physical heap storage to grow because deleted elements may remain inside the heaps until they reach their roots.

To control this growth, the implementation uses periodic purging.

Let:
- H = total number of physical heap entries.
- L = total number of live readings.
- α = purge factor.

The implementation uses a default purge factor of 2.0.

Purging is performed when:

    H > α × L

During purging:

1. Traverse the physical entries in both heaps.
2. Keep only entries that are still active.
3. Rebuild both heaps using the remaining active entries.
4. Reset the dead-item counter.

This prevents deleted entries from accumulating indefinitely.

## 10. Correctness Argument

We prove that the two-heap method returns the correct percentile after rebalancing.

Initially, both heaps are empty, so the size, ordering and membership properties hold.

Assume that before an update:

- L contains the k smallest active readings.
- R contains all remaining active readings.
- Every element in L is less than or equal to every element in R.

After an insertion or retraction, the number of active readings may change.

The algorithm updates the required size of L and rebalances the heaps.

If L contains too many elements, its maximum element is moved to R.

If L contains too few elements, the minimum element of R is moved to L.

These movements preserve the ordering property because the elements being moved are the boundary elements of the two heaps.

Invalid readings are ignored during cleanup, so only active readings contribute to the live partition.

Consequently, after rebalancing:

- L contains the required number of smallest active readings.
- R contains the remaining active readings.
- The ordering and size properties are restored.

Therefore, by induction, the invariants hold after every update.

Since L contains the k smallest active readings, its maximum element is the k-th smallest reading.

Hence, the root of L gives the required percentile.

The method is correct.

## 11. Time and Space Complexity

| Operation | Time Complexity |
|---|---|
| Insert a reading | O(log n) for a fixed percentile |
| Retract a reading | O(log n) amortized under the purge policy |
| Read the median after balancing | O(1) |
| Read a percentile after balancing | O(1) |
| Rebalance after a fixed-percentile update | O(log n) |
| Rebalance after changing to a different percentile | Depends on the number of elements moved; worst case O(n log n) |
| Purge | O(n) when performed |
| Space complexity | O(n) under the purge policy |

A purge takes O(n) time when performed, but its cost is spread across updates through the purge threshold.

## 12. Conclusion

The two-heap method maintains the running median and supports general percentile queries using a Max-Heap and a Min-Heap.

The Max-Heap stores the required smaller portion of active readings, while the Min-Heap stores the remaining larger readings.

A hash table supports identification of readings for arbitrary retraction, lazy deletion avoids searching inside heaps, and periodic purging controls physical storage growth.

The method supports efficient insertion, retraction, sliding-window expiration and percentile retrieval while maintaining the required ordering and size properties.
